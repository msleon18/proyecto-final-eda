# Documento Final - Visualizador Interactivo de Estructuras de Datos **Autor:** Maycol Leon (msleon18) **Curso:** Estructuras de Datos y Algoritmos 2.1 ## 1. Alcance del sistema Este proyecto es una plataforma web interactiva que permite visualizar y manipular cinco estructuras de datos fundamentales en tiempo real: Pila, Cola, Arbol Binario de Busqueda, Heap y Grafo. Cada estructura cuenta con una interfaz visual donde el usuario puede ejecutar sus operaciones principales (insertar, eliminar, buscar, recorrer) y ver el resultado reflejado de inmediato en pantalla. Cada operacion que el usuario realiza se envia a un backend que ejecuta la logica real de la estructura y guarda un registro de la operacion en una base de datos PostgreSQL, permitiendo mantener un historial consultable de todo lo ocurrido en cada estructura. ## 2. Tecnologias utilizadas | Capa | Tecnologia | Justificacion | |---|---|---| | Frontend | React + Vite | Permite construir interfaces reactivas que se actualizan automaticamente cuando cambia el estado de una estructura, ideal para animar operaciones paso a paso | | Backend | Node.js + Express | Mismo lenguaje que el frontend (JavaScript), facil de desplegar, con un ecosistema maduro de librerias para conectarse a bases de datos relacionales | | Base de datos | PostgreSQL (alojado en Supabase) | Soporta transacciones ACID de forma nativa y el tipo de dato JSONB, ideal para guardar el estado de una estructura (como un arbol o un grafo) en una sola columna | | Despliegue backend | Render | Plan gratuito suficiente para un proyecto academico, despliegue automatico desde GitHub | | Despliegue frontend | Netlify | Despliegue automatico desde GitHub, variables de entorno faciles de configurar | ## 3. Arquitectura general ``` Frontend (React, Netlify) | | HTTP/REST (axios) v Backend (Express, Render) | | pg (node-postgres) v Base de datos (PostgreSQL, Supabase) ``` Cada estructura de datos sigue el mismo patron de capas: 1. **Estructura pura** (`backend/src/structures/`):  2. **Rutas/Endpoints** (`backend/src/routes/`): exponen la estructura como una API REST y guardan cada operacion en la base de datos. 3. **Componente visual** (`frontend/src/components/`): consume la API y dibuja el estado actual de la estructura. Esta separacion permite que cada capa se pueda entender, probar y explicar de forma independiente. ## 4. Justificacion de las estructuras elegidas ### Pila (Stack) Se eligio por ser la base de patrones como deshacer/rehacer y la pila de llamadas de un programa. Su operacion caracteristica (LIFO: el ultimo en entrar es el primero en salir) se implemento con un arreglo donde `push` y `pop` operan siempre sobre el ultimo elemento. ### Cola (Queue) Se eligio como contraste directo con la Pila: mientras la Pila es LIFO, la Cola es FIFO (el primero en entrar es el primero en salir), lo que la hace ideal para simular sistemas de turnos o colas de impresion. Ademas, la Cola es la base necesaria para implementar el recorrido BFS del Grafo. ### Arbol Binario de Busqueda (BST) Se eligio para representar una estructura jerarquica y ordenada. A diferencia de un arreglo, un BST permite busquedas en tiempo O(log n) en el caso promedio, ya que en cada nodo se descarta la mitad del arbol restante. ### Heap (Min-Heap) Se eligio como segunda estructura de arbol para mostrar un caso de uso distinto al BST: una cola de prioridad. A diferencia del BST, el Heap no mantiene un orden total, solo garantiza que la raiz sea siempre el elemento minimo, lo que lo hace mas eficiente para casos donde solo se necesita acceder repetidamente al menor valor (por ejemplo, en algoritmos de planificacion). ### Grafo (con BFS y DFS) Estructura obligatoria segun la rubrica. Se eligio representarlo como una lista de adyacencia por ser la forma mas eficiente en memoria para grafos poco densos. Se implementaron los dos recorridos clasicos (BFS por anchura, usando una cola; DFS por profundidad, de forma recursiva) para poder comparar visualmente como cada uno explora el mismo grafo de forma distinta. ## 5. Persistencia y transacciones Cada operacion exitosa sobre cualquier estructura se guarda en una tabla unica llamada `operaciones`, con las columnas: estructura, tipo_operacion, valor, estado_resultante (snapshot en JSON del estado tras la operacion) y fecha. Ademas, se implemento un endpoint de reinicio (`/api/stack/reset`) que demuestra el uso explicito de una transaccion SQL: dentro de un mismo bloque `BEGIN...COMMIT` se borra el historial de la estructura y se inserta un registro de reinicio. Si cualquiera de las dos operaciones falla, se ejecuta un `ROLLBACK` que revierte todo el bloque, garantizando que la base de datos nunca quede en un estado intermedio inconsistente (atomicidad). ## 6. Despliegue - Frontend: https://iridescent-treacle-8d3e02.netlify.app - Backend: https://proyecto-final-eda.onrender.com - Repositorio: https://github.com/msleon18/proyecto-final-eda ## 7. Limitaciones conocidas - El estado de cada estructura se guarda en memoria dentro del servidor backend; si el servidor se reinicia (algo que ocurre automaticamente en el plan gratuito de Render tras periodos de inactividad), las estructuras vuelven a su estado vacio, aunque el historial de operaciones en la base de datos se conserva. - El plan gratuito de Render "duerme" el backend tras un periodo sin uso, por lo que la primera peticion tras la inactividad puede tardar hasta 50 segundos. - Si el guardado de una operacion en la base de datos falla (por ejemplo, por un corte de red), el cambio en memoria ya se aplico antes de intentar guardar, lo que puede generar una breve desincronizacion entre el estado visible y el historial. Una mejora futura seria revertir el cambio en memoria si falla el guardado.
